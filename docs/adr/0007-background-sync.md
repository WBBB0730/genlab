# 收取只在后台进行：命令结束与开始等待时启动后台收取进程，全库只有一个收取者

kie 的产物 14 天后失效，所以库里生成中的版本要尽早收下。原先每条命令运行前先把全库生成中的版本查一遍、下载完，再做命令本身的事；现在改为命令结束时启动一个后台收取进程（隐藏命令 `sync`），命令本身不等它。后台进程每 5 秒重新扫描整个库，收下已完成的生成，全部收完或运行满 30 分钟后退出，下一条命令再启动。

全库同一时间只有一个收取者，靠库根目录下的 `.sync.lock` 互斥：已有收取者时新启动的立即退出。等待（生成命令的等待阶段与 `wait`）开始时也启动后台收取进程；等待本身只读记录，到时直接返回，不中断任何收取。

在前台收的时候，收取的耗时没有上限：网络慢或断开时，连只读命令也被拖住；大文件的下载让命令超出自己的等待上限。改为只在后台收取后，命令的耗时与网络、与其他项目都无关，命令什么时候结束（包括被 agent 提前结束）都不影响收取。做法与 git 的自动维护（默认在后台进行）、update-notifier 的后台检查一致。

## Considered Options

- **仍在前台收全库，但限时、计入命令的超时**：实现简单，但每条命令都要多花这段时间，大文件可能要跨几条命令才收完。被否。
- **等待时没有收取者就由前台自己收，到时中断下载**：多一条收取路径，还要把中断传进每次查询与下载；等待开始时启动后台收取，已能保证等待期间有人在收。被否。
- **只收当前项目**：其他项目不再拖慢命令，但某个项目 14 天内没人用，它的产物就会过期。被否。
- **取消隐式收取，只在等待时收**：最简单，但中断后要靠 agent 记得运行 `wait` 才能补回。被否。
- **注册系统定时任务（如 git maintenance）**：不运行任何命令也能收，但每个系统的计划任务都要单独安装与卸载。暂不采用，以后需要时可作为补充。
- **常驻服务或 kie 回调**：回调需要公网地址，常驻服务对本工具过重。被否。

## Consequences

- 后台收取没有输出：收下的结果与失败原因写进版本记录；查询或下载出错时不报警告，留到下一轮重试，等待期间只看到版本仍在生成中。
- 查看类命令（`show`、`list`）显示的是记录的当前状态，要拿到结果仍用 `wait`。
- 后台进程沿用当前进程的 node 与启动参数，经 npx、全局安装、开发时的 tsx 运行都适用。
- 后台进程被提前结束时不影响正确性：下一条命令或下一次等待会再启动它。
